# MoeKoeIsland 灵动岛

给 MoeKoe Music 配的桌面歌词组件：**屏幕顶部灵动岛 + 任务栏歌词条**。

## 仓库结构

```
manifest.json                插件清单（仓库根目录即插件包根目录）
background.js / bridge.html / bridge.js / popup.html / popup.js   扩展端
icons/                      插件图标
bin/win32/MoeKoeIsland.exe  native host 二进制（由 manifest 的 moekoe_native_hosts 引用）
native-host/                ↑ 该二进制的完整源码与构建配置（见 native-host/README.md）
```

> `native-host/` 提供 `bin/win32/MoeKoeIsland.exe` 的全部源码与 PyInstaller 配置，
> 其编译结果与仓库内二进制的内嵌字节码逐项一致，便于审核与复现构建。

## v1.7.24 重点（拖到屏幕右侧「右边陷进去」根治：空帧预夹）

**需求**（2026-10-10）：「那个灵动岛拖到右侧的时候右边直接陷进去了，你帮我修正一下」

### 根因：锚定态胶囊向右生长 + 换句动画窗口不动

锚定态（`CFG['x']` 有值）胶囊贴窗口左缘、向右生长；v1.7.20 起换句动画期间
窗口「只重绘、绝不动」。岛停在屏幕右侧、下一句更长时：

```
胶囊右缘 = CFG['x'] + 新胶囊宽  →  长出屏幕右缘，且永不回夹
```

实测溢出 **406px**（上限 ≈ TEXT_W_MAX − 旧槽宽 ≈ 600px）。
拖动夹取本身没问题（E1 实测贴缘准确）；溢出全发生在**换句变宽**时。

### 修法：空帧预夹（`_reclamp_for_slot`）

在「收缩→展开」交界帧（槽宽=0、透明度=0，**屏幕上没有胶囊**）：

1. 按**目标槽宽**算出最终胶囊宽，把窗口一次性移到「放得下」的位置；
2. 锚定态同步修正 `CFG['x']`（保持「胶囊左缘 == CFG['x']」不变量）；
3. 一次性移动发生在空帧上 = 肉眼不可见；展开过程窗口照旧纹丝不动
   （**不回退** v1.7.20 零抖动）。挂载点：`_advance_swap` 交界帧、
   `_settle_swap`（暂停落位）、`_apply_metrics` 空闲态（字体/布局变更）。

顺带修复**松手弹一下**：stay 落位改瞬时 `move + repaint`（旧版 200ms 动画
期间胶囊先左跳 (cw_win−cw)/2 ≈ 231px 再滑回）。

## v1.7.23（历史）拖动时「歌词偏向一边」根治：文字跟胶囊

**需求**（2026-10-10）：「这个灵动岛拖动的时候歌词不固定，歌词会偏向左边或者右边，能不能拖动的时候随时固定歌词的状态」

### 根因：文字锚点与胶囊解耦

歌词文字的屏幕锚点 = `_cap_left_ideal()`（解析理想位置），两种态下都是
**与窗口当前位置无关**的常数：

| 态 | `_cap_left_ideal()` | 胶囊（paintEvent） |
|---|---|---|
| 顶格居中（`CFG['x']` 松手才写入） | 屏幕中心对称 `(SW−cw)/2` | 窗口实际位置（跟鼠标） |
| 拖动锚定（`CFG['x']` 有值） | 常数 `CFG['x']` | 窗口实际位置（跟鼠标） |

拖动时胶囊跟鼠标走、文字钉在常数位置 → 相对岛偏向一边，拖多远偏多远
（插桩实测偏差最大 **1112 / 1305 px**）。次要：拖动中换句收尾
`_apply_current_size → move(target_pos())` 会把窗口拽回 `CFG['y']` 旧值。

### 修法：拖动 = 文字跟胶囊

`_poll_input` press 时置 `_dragging=True`、release 复位。拖动期间：

1. `_cap_left_ideal()` 改取**窗口实际位置**（`self.x()+pl`）→ 文字与胶囊同源，
   拖动全程相对关系恒定（= 用户要的「随时固定歌词的状态」）；
2. `target_pos()` 原地短路 → 换句收尾/高度切换不再拽动窗口；
3. 松手复位 → `_snap_now` / `animate_to_target` 照常用理想位置落位。

### 验收（`probe_drag.py`，center/anchored 双场景 × 插桩直查）

拖 ~1400px、跨 4 次换句：

| 判据 | v1.7.22（旁路复现） | **v1.7.23** |
|---|---|---|
| D5 拖动中文字锚点相对胶囊 | **1112 / 1305 px** | **0.0 px** |
| D2 垂直跟手 | — | 0.5 px |
| D3 松手 snap 落位 | — | CFG['x'] == 胶囊左缘 ±1，落位后静止 |
| D1/D4 文字带 ink / 屏幕连续 | — | 极差 0px / 无单帧跳变 |

**回归**：`verify_v1712_island` 6/6 · `verify_v1718_island` 13/13 · `edge_island` 9/9 ·

## v1.7.22（历史）切歌「上一首多跳一次」根治：歌词持有窗口

**需求**（2026-10-10）：「自动到播放到这首歌歌尾了，到下一首的时候还会多跳出来上一首歌曲一次，灵动岛和任务栏都是这样子」

### 根因：WS 推送时序竞态

`playerState` 包**只带 isPlaying + currentTime、不带歌曲标识**。切歌瞬间：

1. 下一首的 `playerState`（currentTime≈0）**先到** —— 内存里还是上一首的歌词；
2. `current_line(旧歌词, 0ms)` 恰好命中**上一首的第 0 句** → 岛/任务栏显示它（= 多跳出来一次）；
3. ~250ms 后 `server-lyrics`（歌+歌词同包）到达 → 再换一次。

无歌词/慢歌词歌曲有第二形态：换歌包不带歌词时旧歌词残留在内存，同样跳一次。

### 修法：歌词持有窗口

- 检测「进度大幅回跳 >1s」（`apply_state`，换歌/回跳 seek 的唯一可靠信号）
  → 把显示用进度时钟 `now()` **冻结**在回跳前的值（`lyric_hold/hold_time`）：
  全部 9 个显示侧调用点（选行/卡拉OK/滚动/任务栏）都经由 `now()`
  → 一处冻结、整块显示完全一致地静止在「上一首末尾」；
- 新歌词包到达（`apply_lyrics` 解析出新 lines）即解冻 → 一次干净换句；
- 换歌且新包不带歌词 → **丢弃失效旧歌词**（显示歌名）并解冻；
- 2s 安全超时：新歌词迟迟不来则自行解冻（宁换勿卡）；
- 误伤面：同歌内回跳 seek >1s → 只冻 ≤250ms（下个 server-lyrics 包就解冻）。

|---|---|---|
| H1 持有窗口显示恒为旧歌末句（岛） | **跳回旧歌第 0 句** | **恒定** |
| H1b 任务栏取词 | **同样跳回** | **恒定** |
| H2 窗口内逐像素 | **12607px 差异** | **0px** |

**回归**：`verify_v1712_island` 6/6 · `verify_v1718_island` 13/13 · `edge_island` 9/9 ·

## v1.7.21（历史）暂停 = 全静止

**需求**（2026-10-10）：「这个灵动岛暂停的时候它会跳一下才静止，暂停的时候灵动岛要做到全静止状态」

### 暂停瞬间的 4 个跳变源（`probe_pause.py` 六场景逐帧取证）

| # | 场景 | 机理 | 实测单帧突跳 |
|---|---|---|---|
| ① | 普通歌词行（无逐字时间戳） | `paintEvent` 暂停时把文本拼成 `'‖ ' + body`，槽内居中 → 整行平移 | **625px** |
| ② | 无歌词（歌名兜底） | `_want_texts` 暂停时返回 `'‖ ' + txt` → 文本变化 → 触发落位 | **4850px** |
| ③ | 换句收缩中途暂停 | v1.7.12「立刻落位」：槽宽 88→259、透明度 0.73→1.00 一帧完成 | **170.8px（\|Δslot\|）** |
| ④ | 长句跑马灯滚动中暂停 | v1.4.3「暂停整句可见」特判：偏移瞬间跳到 travel | 几十~上百 px |

（卡拉OK行、展开中途暂停两个对照场景本来就不跳 —— 高亮冻结、在飞展开自然收尾。）

### 修法：暂停 = 全静止

1. **①② 撤掉 `'‖ '` 前缀**：暂停态由「卡拉OK高亮冻结 / 封面停转」表达，文字保持原样；
2. **③ 不再立刻落位**：正在飞的收缩/展开**自然跑完**（连续运动，跑完即静止）；
   只有暂停中**空闲态**下文本真的变了（暂停中拖进度/换歌）才落位 —— 唯一例外；
3. **④ 跑马灯暂停冻结在当前位置**（SPlayer 同语义），恢复播放后从冻结处继续滑完。

## v1.7.20（历史）「抖动」结构性根治：窗口几何刚性化

**需求**（2026-10-10 第四次反馈）：「灵动岛歌词展开的时候歌词依然还是会有抖动，要做到无抖动」

### 前三版为什么都没修好

| 版本 | 修的是什么 | 结果 |
|---|---|---|
| v1.7.17 | 展开曲线过冲（「震动」） | 引入「闪动」 |
| v1.7.18 | 曲线形状（快起 + 零过冲） | 抖动仍在 |
| v1.7.19 | 文字原点「屏幕绝对坐标取整一次」 | **用户明确表示仍然抖** |

因为真凶根本不在**坐标**，而在**时序**。

### 真凶（`probe_desync.py` 真屏取证，每帧抓屏两次）

`pre` = `tick()` 后立刻抓（重绘还没发生），`post` = `repaint()` 强制同步重绘后再抓，
在文字带上求两者 ink 掩码的最佳配准位移：

```
Δgx = -36 → 配准 -36      Δgx = +55 → 配准 +55
Δgx = -25 → 配准 -25      Δgx = +36 → 配准 +36
```

**配准位移恰好 = 本帧窗口位移 Δgx**（38/73 帧非零，单帧最大 55px）。
同时 618/618 帧 `Qt.x/y == Win32 GetWindowRect()` —— 窗口位置本身是准的。

机理：`move()/setFixedSize()` 立即生效（SetWindowPos），而重绘要等事件循环、
本身还要 5~15ms 才提交（CJK 冷栅格化昂贵）→ 每帧都有一段
「窗口已跳到新位置、画布还是上一帧」的中间态，把整块内容顶偏 Δgx。
v1.7.19 让文字反向补偿窗口位移，反而把中间态的偏移**放大**成了整个窗口位移。

### 修法：窗口几何刚性化（`RIGID_WIN = True`）

* 窗口恒按**最大槽宽** `TEXT_W_MAX=720` 预留（`win_content_w()`，实测 844px），位置恒定：
  `gx = 屏宽/2 − MARGIN − 预算宽/2`（与槽宽无关的常数）；
* 胶囊在窗口内**居中绘制**（`_pill_left_local()`）→ 屏幕上的胶囊照旧左右对称生长；
* 动画期间只 `self.update()`，**绝不** `move`/`setFixedSize`。

于是「重绘迟到」的最坏结果只是**屏幕上重复上一帧** —— 任何一帧都是合法连续画面，
物理上不可能出现位移。

配套改动：

1. **WM_NCHITTEST 逐点命中**：胶囊实心区 → `HTCLIENT`，其余（含透明边距）→ `HTTRANSPARENT`
   （与任务栏组件同一套做法）。刚性宽窗多出的透明区域不再吃点击，
   不然顶格居中时正好压住最大化窗口的标题栏/浏览器标签区；
2. 拖动 / 吸附 / 命中判断全部改按**胶囊**坐标系（窗口≠内容区了）；
3. `target_pos()` 拖动锚定态改按**胶囊右缘**夹取，恢复被刚性宽窗压缩的可拖行程
   （2560 屏实测回到 2350）；
4. 尺寸真变（配置变更/双行高切换）仍走 `setFixedSize + repaint()`，把中间态压到微秒级。

### 验收（`verify_v1720_jitter.py`，量具本身也重做了）

v1.7.19 的两条断言是**量具错误**：K4「全带文字重心」、K5「全胶囊区配准」都把
「新字被露出来」和「opacity 淡入」算成了位移。本版换成两条更硬的判据：

| 断言 | v1.7.19（A/B 复现） | **v1.7.20** |
|---|---|---|
| K1 动画期间窗口 Δgx | **最大 28px** | **≡ 0** |
| K5 opacity=1 帧对 × 裁剪框交集差异像素 | **4731 px** | **0 px（90 对）** |
| K2 Qt.x/y == Win32 GetWindowRect | 一致 | 一致（0/1024） |
| K3 胶囊中心 = 屏幕中线 | 偏差 0.50px | **0.00px** |
| K4 露出边单调（左只向左/右只向右） | 0 次倒退 | 0 次倒退 |
| K7 文字屏幕整数 x 逐帧恒定 | 恒定 | 恒定 |

**K5 是关键**：把相邻两帧都裁到「裁剪框交集」（去掉两边 3px 边缘）、只看 opacity 已经
到 1 的帧对 —— 文字钉死在整数屏幕坐标上，交集内的可见字形必须**逐像素完全一致**。
旧版差 4731px = 整块内容被窗口位移顶偏；新版 0px = 一 个 像 素 都 没 动。

时空切片（`evi_filmstrip.py`，真屏**固定区域**逐帧堆叠）：新版文字笔画在所有帧里
完全垂直对齐（一条笔直竖线、零锯齿）；旧版同一位置可见窗口逐帧跳动。

**回归**：`verify_v1712_island` 6/6 · `verify_v1718_island` 13/13 · `edge_island` 9/9 ·
`verify_v1716_scroll` 11/11（任务栏不动）· `verify_v1720_func` 6/6
（窗口宽度刚性 / 胶囊居中 / NCHITTEST 穿透 / 拖动行程）。

**本版只改窗口几何的驱动方式**：展开曲线、收缩时长、淡入淡出、暂停行为、任务栏全部原样保留。

## v1.7.19（历史）灵动岛换句「抖动」彻底消除 —— 一次取整

**需求**（2026-10-10）：「这个抖动依然存在，能不能给它做到完全消除？」

**注意**：这是和前几轮**不同**的一个 bug。v1.7.17 修的是「展开曲线的过冲（震动）」，
v1.7.18 修的是「展开曲线的形状（闪动）」，两者都在**曲线**上；
本版的「抖动」在**坐标取整**上 —— 曲线怎么调都不会好。

### 现场（`probe_geom.py`，逐帧记录窗口几何 + 文字原点的屏幕绝对横坐标）

compact 版式、开翻译、屏幕居中、150% 缩放，取展开段（500ms，槽宽 619 → 643px，13 帧）：

| 量 | 逐帧差分 | 符号翻转 |
|---|---|---|
| 胶囊左缘 | −37, −18, −19, −20, …（全部同号） | **0 次** |
| 胶囊右缘 | +36, +19, +19, +20, …（全部同号） | **0 次** |
| **文字屏幕绝对横坐标** | 982→**981**→982→**981**→982→… | **7 次** |

即：**胶囊在平滑地生长，字却在 ±1px 来回弹** —— 这就是用户看到的「抖动」。

像素级同样能抓住（同一固定屏幕绝对窗口，与首帧比对，阈值 30）：

| 帧 | 2 | 3 | 4 | 5 | 10 | 12 |
|---|---|---|---|---|---|---|
| v1.7.18 差异像素 | **926** | 48 | 55 | 61 | **1033** | 130 |
| v1.7.19 差异像素 | 37 | 48 | 61 | 77 | 126 | 130 |

旧版帧 2 / 帧 10 的差异是邻居的 ~15 倍 —— 那是**整行字形相对固定屏幕列平移了 1px**。

### 根因：两次独立、相位不同的取整

文字的屏幕绝对横坐标 = ① 窗口位置（整数）+ ② 窗口内文字原点（整数），而这两个整数是分开算的：

1. `target_pos()` 用 `(屏宽 − cw) // 2`（**floor**）→ 随 cw 每 +1 走出 0/−1 的台阶，
   并带 0~0.5px 的量化误差，且**误差符号随 cw 奇偶逐帧翻转**；
2. `_px(x + (sw − w)/2)` 在**窗口局部**坐标 round → 另一次 0/1 台阶。

两条台阶的相位不一致 → 求和后残留 ±1px 的「拍频」。
（v1.7.10 的 `_px()` 只治了**子像素发虚**，没治这个**整数拍频**。）

### 修法：把「绝对坐标」写成恒定的浮点值，只取整一次

compact 下 `cw = PAD + DISC + 18 + sw + PAD + 4`，`x_local = MARGIN + PAD + DISC + 18`，于是

```
理想绝对原点 = (屏宽 − cw)/2 + (PAD + DISC + 18) + (sw − w)/2
             = 屏宽/2 + (DISC + 14 − w)/2          ← 与槽宽 sw 无关，恒定
```

`round()` 之后就是个**常数**：文字在屏幕上纹丝不动，槽只负责对称地露出 / 盖住它
—— 这正是 SPlayer `.lyric{justify-content:center;overflow:hidden}` 的行为。

新增两个方法（`Island`）：

* `_cap_left_ideal()` —— 胶囊左缘在屏幕绝对坐标下的**理想** x（浮点、平滑、未取整），
  与 `target_pos()` 共用同一套公式与夹取范围；
* `_px_abs(abs_x)` —— 在**屏幕绝对坐标**取整**一次**后折回窗口局部坐标
  （`round(abs_x) - self.x()`）。窗口位置那 0~0.5px 的量化误差被彻底吸收在窗口上，不再漏进文字。

`_draw_text`（普通文本）与 `_draw_karaoke`（逐字高亮）两条绘制路径同步改用。
`_px()` 保留原样（静止态、非伸缩场景仍在用），文档里补了一句「局部取整治不了这个抖动」。

## v1.7.13 重点（超宽行不再横向跑马灯，改右端省略号）

**需求**（2026-10-09）：「任务栏那边播放的时候歌词不要搞滚动，直接显示两行歌词播放状态」。

| `_draw_prom()`（换句放大） | **先在主行字号下省略到 `w`** 再预栅格化 → 贴图宽 = 省略宽 × s ≤ w（s ≤ 1），动画期无需裁切/位移；`s=1.0` 那帧与静止态 `_line()` 的省略结果**逐像素一致** |

## v1.7.12 重点（暂停不再「再伸缩上一句」+ 任务栏换句不再「黑白闪」）

### ① 灵动岛：暂停时把【上一句】又伸缩一遍

**症状**：暂停时，在**歌词较快**的歌里，灵动岛还会把**上一句**的歌词再伸缩一遍。

**两层成因**（缺一不可，两个都修了）：

| 层 | 机理 | 证据 |
|---|---|---|
| 观感 / 主因 | 「收缩 250ms → 换文本 → 展开 500ms」是**播放中的转场**。快歌每句只有几百 ms，岛**一大半时间停在动画中途**。一按暂停，若正处「收缩」阶段，旧代码会把这轮**跑完**（屏幕上还是上一句）；暂停带来的重同步还可能让目标句来回翻 | 真 16ms 事件循环实测：暂停点恰在 `expand 中途 / w=126.9 / 屏幕上仍是第04句`；旧版本随后 `idle→shrink(第04句) → shrink→expand(第05句)`，**完整又跑一轮** |
| 进程层 | MoeKoe **全项目只在 play/pause 事件推一次 `playerState`**（`electron/main.js` 的 `play-pause-action` → `apiService.updatePlayerState`，唯一调用点）。播放中的 ~250ms 进度对齐（`server-lyrics`，由 `PlayerControl.vue` 的 `updateCurrentTime` throttle 200ms 推送）**在暂停那一刻断掉**；上报的 `audio.currentTime` 是 HTMLAudioElement 采样值，比客户端外推值**略早**，快歌里足以跨过句界退回上一句 | 注入「暂停上报偏早 250ms / 600ms」两种现实姿势复现 |

**修法**（对标 SPlayer-Next）：

- `_advance_swap()`：**暂停时一律不播换句伸缩**——只要屏上的字 ≠ 此刻该显示的字（或正处于收缩中途），
  立刻落到目标句，等价 SPlayer `windows/dynamic-island/App.vue` 的 `applyImmediate()`
  （它在「不适合播动画」的场合也是**直接到位、不收缩**）。文本已一致、只是展开收尾时**不打断**。
- `apply_state()`：从「播放 → 暂停」这一步，进度取 `now()` 外推值与上报值的**较大**者
  （歌词时钟只前不后）；差值 **> 0.75s** 说明用户真的往回拖了进度（seek），照实接受。

**验收**（`verify_v1712_island.py`，真 16ms 事件循环、快歌 400ms/句带逐字时间戳）：

|---|---|---|

| 偏早 250ms | **0** | 第05句 |

### ② 任务栏：换句「放大」跳转时黑白闪一下

**症状**：放大歌词跳转时会「黑白」闪一下，希望「**让蓝字自由过渡**」。

**根因**：那 0.4s 的换句过渡**整段用 `base`（任务栏主题的黑/白主文字色）上色**，
而静止态逐字卡拉OK**唱满**用的是 `accent`（蓝 `#2F80ED`）。于是：

- 换句**第一帧**：整行刚唱完的**蓝字唰地变成黑/白**（首帧闪）；
- 过渡**末帧**：新行从满不透明掉回卡拉OK「**未唱**」暗色（`base@0.55`）（末帧闪）。

一头一尾两次颜色跳变 = 用户说的「黑白闪」。**参照 SPlayer-Next `windows/taskbar-lyric/App.vue`**：
那边 `.line-move / .line-enter-active / .line-leave-active` 过渡
`transform / opacity / font-size / color`，且**过渡期整行统一 `color`，不做卡拉OK色差**——
正是「蓝字自由过渡」的做法。

**修法**：过渡期沿用**两端各自的真实颜色**：

| 端点 | 取值 | 理由 |
|---|---|---|
| 离场旧行 | `old_col_base` = `accent`（旧行是卡拉OK时）或 `base`；`old_a0` = **它上一帧静止态的不透明度** | 否则动画第一帧就「暗一下」 |
| 新主行落点 | `prom_a1` = `base@0.55`（卡拉OK）/ `base`（普通） | 与 `_draw_karaoke_line` 的 unsung **同一公式**，0.4s 结束时严丝合缝 |

三个分支（`can_queue` / `bilingual_bridge` / **`else`**）全部改齐。**`else` 分支才是本机最常走的一条**
（compact 版式 + 当前句没有译文 → 没有第二行槽位），旧代码那里写死 `base@210`，正是用户实际看到的闪。

**实测**（`verify_v1712_tb.py`，真事件循环、逐帧记录 `_line / _line_fx / _draw_prom` 的
实际颜色与有效不透明度，并与**窗口前后紧邻的静止帧**逐值比对）：

| 来到的主行 · 过渡末帧 | `#f6f6f8` a=**255**，静止态 a=140 → **Δalpha = +115** ❌ | `#f6f6f8` a=**140**，静止态 a=140 → **Δalpha = 0** ✅ |

## v1.7.11 重点（任务栏「放大」过程从「卡顿」变「流畅」）

用户反馈的是**放大过程本身不流畅**。实测把它拆成**两个互相独立**的成因，
两个都修了 —— 只修任何一个，看感都还是卡的。

### ① 换句动画**没有帧投递**（结构性缺陷）

- **问题现场**：换句放大的时间轴写在 `paintEvent` 里（`time.time() - self._fade_t0`，
  窗口 `0.40s`，照 SPlayer 的 `.line-move`）。但 **`paintEvent` 不会自己触发自己** ——
  必须有谁在这 0.4s 里反复 `update()`。而 `tick()` 的重绘条件只有三个：

  ```
  _karaoke_active()  → 本句要带「字级时间戳」
  _marquee_active()  → 整句宽度超出文本区
  maybe_refresh()    → 内容 key 变了（换句期间只变一次）
  ```

  于是**纯 LRC 歌曲**（无逐字时间戳、句子又放得下）在换句那 0.4s 里
  **一帧都不重绘**。实测（`flow_probe.py`，3.85s 连续采样）：
  总共只有 **5 次** `paintEvent`，每个换句窗口**跨度 0.0ms / 只有 1 帧**，
  主行字号序列全是 `10.00` —— 这个「放大」**根本没播出来**，只有一次生硬跳变。
- **修法**：新增 `_swap_active()`（判据用 `_fade_t0` 而非 `_fade_from` ——
  后者在**动画结束那一帧**会被 `paintEvent` 清掉，而那一帧恰恰是必须画出来的
  最后一帧；多留 50ms 余量兜住），`tick()` 里**优先** `self.update()`。
  对标 SPlayer：那边只改一次 class 列表，**浏览器自己**保证过渡期间每一帧都合成；
  这里做等价动作。
- **实测**：纯 LRC 换句窗口 **1 帧 → 26 帧**，帧间隔 p50 **16.0ms**
  （60fps 满帧），`s` 序列 0.800 → 1.0000 单调、**零步数 0**、Δcy 单调不回头。

### ② 逐帧 `setPointSizeF` 被 grid-fit hinting 量化（真正影响听感的那个）

- **问题现场**：v1.7.9/v1.7.10 是**逐帧插值字号**再 `drawText`。
  实测（`probe_grow.py`，真实动画字号序列 8.0→10.0 / 26 帧）：
  Qt 的 grid-fit hinting 会把同一串文字的字形**量化成极少数几档** ——
  行宽按 **7px 整数台阶**跳（119→126→133→140→147，= 7 个字 × 每字 1px），
  **25 帧里有 21 帧墨迹完全不变**。也就是说放大实际是「**几下猛跳 + 后 40% 静止**」，
  这才是肉眼看到的「卡顿 / 不够流畅」——**不是掉帧**（帧投递实测是满 16ms）。
  而且每帧都是新字号 ⇒ 每帧**冷栅格化**整串 CJK，单帧 p90 约 4ms。
- **修法**：照 SPlayer `.line-move` 的语义（那一行的 `font-size` 是**连续过渡**的，
  浏览器靠连续轮廓缩放实现）—— 把主行**按主行字号栅格化一次**成一张小位图
  （每次换句只做一次，约 0.3ms，之后 25 帧全部命中缓存），
  动画期按 `s = 当前字号 / 主行字号`（0.8 → 1.0）**整幅缩放贴图**。
  - 水平锚**左缘**＝`transform-origin: left center` 的 `left`，用位图内笔原点精确定位；
  - 垂直锚**内容中心**，由静止态基线公式反推（`_line()` 同一公式）；
  - 坐标锚点全部吸附整数设备像素（沿用 v1.7.10 的 `_px`）。
- **实测**（`probe_raster.py` / `verify_v1711.py`）：

  | 指标 | v1.7.10 逐帧改字号 | v1.7.11 位图缩放 |
  |---|---|---|
  | 零变化帧数（25 帧中） | **21** | **0** |
  | Δ墨迹变异系数（越小越均匀） | 2.31 | **0.76** |
  | 墨迹宽台阶 | 只有 7px 一档 | 1 / 2 / 3 / 4 px（细密） |
  | 单帧绘制 p90 | 约 4 ms | **0.1 ms** |

  最关键的一条：**`s=1.0` 时是 1:1 贴图 ⇒ 与静止态 `_line()` 渲染逐设备像素相同**
  （`verify_v1711.py` A 项：4 个不同 `cy` 全部 **0** 个差异像素）
  ⇒ 动画结尾**不会**「突然变清晰 / 抽一下」。

### 顺带确认（用你的真实歌曲《百年孤寂》跑了一遍）

- 该曲 49/49 行都带 `chars`（字级时间戳）→ 本来就走 `_karaoke_active()` 满帧，
  所以 ① 那条修复对它**无影响**；但 ② 的字形量化对它同样成立，是本轮真正解决听感的那条。
- 真实歌曲回归（`verify_real_song.py`，16s 真实事件循环）：
  978 帧、换句窗口 **26 帧 / 间隔 p50 16.0ms / p90 16.7ms**，
  `s` 单调、零步数 0，窗口内单帧绘制 p90 ≈ 0.5ms，**超 16.6ms 预算的帧只有 1 帧
  （还是首帧冷启动，见下）**。
- ⚠️ 首帧约 300~380ms 是进程内**第一次**把该字号栅格化进字形缓存（外加封面解码），
  不属于逐帧动画的稳态开销，统计里已剔除。

### 排查过程中被实测**推翻**的三个假设（留档，免得后人重走）

1. 「卡顿 = 掉帧」→ 实测帧投递满 16ms（对带字级时间戳的歌）。真因是**字形量化**。
2. 「关掉 hinting 就能连续」→ `QFont.PreferNoHinting` 在本机 Qt 上**无效**
   （A/B 实测零变化帧数同为 21，行宽仍按 7px 跳）。
3. 「150% 缩放导致逻辑整数取整不足」→ 实测 `QApplication.primaryScreen().devicePixelRatio()
   = 1.0`，进程未启用高 DPI 缩放，**逻辑像素就是设备像素**。据此**回退**了为此引入的
   1/DPR 取整网格（不为修一个不存在的 bug 引入风险）。

## v1.7.10 重点（消除灵动岛换句震动 + 任务栏放大卡顿）

两个毛病其实是**同一类**：绘制坐标落到了**小数像素**上，而 Qt 对小数坐标
会走「子像素定位」——同一个字在不同小数相位下被栅格化成**不同的位图**。

### ① 灵动岛：消除换句时的「震动」

- **问题现场**：「槽内居中」算出的是 `x + (槽宽 − 文字宽) / 2`。换句时槽宽
  每帧都在变，于是文字绘制原点的小数部分是**逐帧翻转**的。实测（`exp_fix.py` /
  `make_px_figure.py`，20 帧收缩+展开序列）：

  ```
  原稿  TEXT_W: 167  166  156  149  140  129  118  106   93   78   63   47   30
  原点x:      89.0 88.5 86.5 80.0 75.5 70.5 64.5 58.0 52.0 44.5 37.0 29.0 20.5
  小数相位:   .0   .5   .5   .0   .5   .5   .5   .0   .0   .5   .0   .0   .5
  ```
  10/20 帧带 `.50` 小数。Qt 走子像素定位 → 字形按当帧相位重新栅格化；
  实测其中 **5/20 帧**的渲染结果与「正确取整」版本不同（最大 **16.0%** 像素不同），
  且整串文字的位置相对理想位置有 ±0.5px 来回摆动 —— 肉眼就是
  「跳转歌词的那一下有震动 / 发虚一下」。
- **修法**：新增模块级 `_px(v) = float(round(v))`，让**所有随动画变化**的
  绘制坐标一律吸附整数像素：
  - `_draw_text`：槽内居中原点、跑马灯原点、基线 `y`
  - `_draw_karaoke`：逐字绘制的**起始 x**（逐字 advance 本身是整数，
    起点整则整行都整）、基线 `y`
- **实测**：拦截真正传给 `drawText` 的 `QPointF`（`diag_px.py`）——
  收缩+展开全程 **0/20 帧**带小数（修复前 10/20）；卡拉OK 行 56 次逐字绘制
  **全部** `frac(x)=0.00, frac(y)=0.00`。位置序列变为干净的整像素位移：
  `89 → 88 → 86 → 84 → 80 → 76 → 70 → 64 → 58 → 52 → 44 → 37 → 29 → 20 → 12`。

### ② 任务栏：消除「放大」过程的卡顿

- **问题现场**：换句放大期间 `_line_fx` 给离场行传了 `scale = 1.0 + 0.025*lift`
  （次行 `0.985 + 0.015*ease`）。一旦 `_line_fx` 里走了 `p.scale()`，
  **Qt 立刻放弃 hinted 字形缓存**，对整串 CJK 逐字做变换栅格化。实测单帧绘制耗时：

  | 变体 | p50 | p90 | max | 换句窗口内合计 |
  |---|---|---|---|---|
  | 修复前（有 `p.scale()`） | 0.60~0.67 | **5.29~6.25** | **7.08~11.74** | 49.9~66.5 ms |
  | v1.7.10（无 scale） | 0.46~0.49 | **0.67~0.98** | **0.77~1.20** | 14.7~16.8 ms |

  换句期间每帧要重画 2~3 行，16.6ms 的 60fps 预算被吃穿 → 掉帧 = 肉眼「卡顿」。
- **修法**：换句绘制**一律不再传 scale**（虚化 `blur` 保留 —— 实测它几乎不花钱：
  `noblur` 17.1ms vs `noscale` 17.2ms）。这也**更贴 SPlayer**：`.line-leave`
  只过渡 `transform`(translateY) / `opacity` / `font-size` / `color`，
  离场行并不做缩放；那个 2.5% 放大只有肉眼不可辨的量级，纯属白花钱。
- **同时**把 `_line` / `_line_fx` / `_draw_karaoke_line` 的基线与滚动原点
  也 `_px()` 吸附整数。这里有个坑：**`_line_fx` 有 `translate(x, cy)` 变换，
  必须对「设备坐标」取整再折回局部坐标**（`bo_x = (_px(x + s*g_x) - x) / s`），
  只对局部坐标取整没有意义 —— 放大期间 `cy` 是连续插值的
  （`48.00 → 47.72 → 46.84 → …`），不处理就会每帧换一次小数相位。

## v1.7.9 重点（任务栏换句补回「放大」）

参照 `SPlayer-Next/windows/taskbar-lyric/App.vue`。**只改了任务栏的换句绘制，其余未动。**

- **顶上来的主行现在会「放大」**
  - SPlayer 的做法：`.lyric-line[data-role=secondary]` 是 `font-size: 0.82×`、
    `[data-role=primary]` 是 `1.00×`；而 `.line-move / .line-enter-active /
    .line-leave-active` 过渡 `transform / opacity / font-size / color`。
    被提升的那一行在列表里是**同一个 key** → Vue 走 `line-move`（移动而非替换）
    → 它「上移一格」的同时把 **font-size 从 0.82× 平滑长到 1.00×**（+22%），
    用的是 `cubic-bezier(0.4,0,0.2,1)` / `0.4s`，与位移**同一条曲线、同一个进度**。
  - 修法：顶上来的主行**直接插值字号**（`f_promoted`：`f_sub` 点数 → `f_main` 点数），
    而不是缩放位图 —— Qt 实测 8.0/8.5/9.0/9.5/10.0pt 墨迹单调递增（+8/+19/+27/+37%），
    而 transform-scale 会把 8~10pt 的小字缩放得发虚。
  - **颜色同步渐亮**：SPlayer 的 `.line-move` 也过渡 `color`（次行 rgba(.5) → 主行 #fff），
    所以主行 alpha 由 `153` 插值到 `255`；不插值的话换句首帧会「突然变亮」。
  - **两端精确落在静止态取值上**，所以既不突缩、也不失放大：
    - `ease=0` → 字号 = `f_sub` 点数、alpha = 153 ⟵ 与上一帧「次行静止」**完全一致**
    - `ease=1` → 字号 = `f_main` 点数、alpha = 255 ⟵ 与下一帧「主行静止」**完全一致**
  - 第 2 行是**翻译**时（`bilingual_bridge`）同样放大：新主行本来也是从次行槽位升上来的，
    统一手感，不看歌词有没有翻译都能看到效果（SPlayer 原版只在"下一句预览"时有这个放大）。
  - 回归：单行 / 无法成队列的兜底分支保持原样（那里没有可提升的次行，不该放大）。

## v1.7.8 重点（修两处「多余的一下」）

都是「换句那一刻不够干净」的小毛病，**只改了这两处，其余行为一律未动**。
参照 `SPlayer-Next/windows/dynamic-island/App.vue` 与 `windows/taskbar-lyric/App.vue`。

- **灵动岛：消除换句瞬间的文字横跳（「卡一下才能对齐」）**
  - 问题现场：换句时的文字对齐方式是**两套**——换句动画期间按 SPlayer 的
    `.lyric` 走「槽内居中 + 两侧对称裁切」，静止播放时却改回**左对齐**。
    切相位那一帧文字会水平横跳 `(槽宽 - 文字宽) / 2`。
    槽被 `TEXT_W_MIN=120` 夹紧时，「你好」（46px）会跳 `(120-46)/2 = 37.0px`，
    「我爱你」（69px）会跳 `(120-69)/2 = 25.5px` —— 肉眼就是「卡一下才能对上」。
  - 修法：对齐方式**全程唯一** —— 动画态与静止态都走 SPlayer 的
    `.lyric { justify-content:center; overflow:hidden; white-space:nowrap }`
    （槽内居中、两端对称裁切）；只有**静止态**且整句真的超过槽宽
    （被 `TEXT_W_MAX` 夹紧的超长句）才退回跑马灯。收缩/展开期间槽宽本来就
    比文字窄（那正是动画本身），**绝不**因此切去跑马灯分支。
  - 实测（同一句「我爱你」→「你好」，104 帧连续采样）：
    帧间最大横跳 **37.00px → 0.50px**（0.5px 纯属像素取整），全程单一 `mode=slot`。
- **任务栏：消除换句末尾的「缩一下字体」**
  - 问题现场：顶上来的主行在整个换句动画里被**恒定放大 4.5%**
    （`focus_scale = 1.045`，已在 v1.7.7 的 exe 字节码里核到 `LOAD_CONST 1.045`），
    动画结束由 `_line_fx` 切回普通单行绘制（`scale=1.0`）时那一帧**突然缩回**
    —— 就是「还要缩小一下字体才能正常播放」。
  - 修法：对齐 SPlayer 的 `taskbar-lyric/App.vue` —— 那里的
    `.line-move` 只过渡 `transform / opacity / font-size / color`，
    `transform` 从 `translateY(y)` 插值到 `none`（同一 scale 矩阵 → **scale 全程恒定**），
    `font-size` 只在 primary(1.0) / secondary(0.82) 之间过渡。
    故把 `focus_scale` 归 `1.0`；`_line_fx` 随即自动回退到原生 `_line` 绘制，动画前后完全一致。
  - 实测（连续三句，23 帧）：主行 `scale` **恒为 1.0000**，结束帧零跳变。
  - ⚠️ **本条已被 v1.7.9 取代**：v1.7.8 把 scale 归 1.0 的同时把「放大」也一起删掉了。
    v1.7.9 改为**插值字号**（`f_sub` → `f_main`），既保住放大、又保持两端零跳变。
    这里保留记录，是为了说明「为什么不能用一个恒定 scale 去表达放大」。

## 安装

1. 打开 MoeKoe Music → **设置 → 插件**
2. 点「**安装插件**」，选择本 zip
   （也可把 `moekoe-island` 文件夹整个放进插件目录后点「刷新插件」）
3. 在插件管理页把本插件的 **本地组件授权** 打开
   （插件需要 `moekoe:nativeHost` 权限才能启动组件）
4. 授权后组件会随播放器自动启动，灵动岛出现在屏幕顶部

## 工作原理

- 组件本体是打包好的原生程序 `bin/win32/MoeKoeIsland.exe`（PyQt5 实现，约 45 MB）
- 由 MoeKoe 以 **native host** 方式拉起，通过 stdin/stdout 交换 JSON Lines
- 歌词数据由组件自己连接 `ws://127.0.0.1:6520` 获取
  （需在 MoeKoe 设置中开启 **API 模式**），
  因此即使不开插件弹窗也能正常显示
- 播放控制优先使用 **SMTC**，不依赖窗口焦点

## 系统要求

- Windows 10 / 11（x64）
- MoeKoe Music 1.6.6 或更高
- 建议在 MoeKoe 设置中开启 **API 模式**

## 配置文件

组件配置与日志位于 `%APPDATA%\MoeKoeIsland\`：

- `config.json` — 位置、吸附、翻译、自启动等设置
- `debug.log` — 运行日志（排查问题用）

弹窗里的「打开配置目录」可直接跳转。

## 常见问题

**灵动岛不出现？**
1. 插件管理页确认本地组件已**授权**；
2. 看弹窗「本地组件」是否为「运行中」；
3. 若显示未运行，可直接双击 `bin/win32/MoeKoeIsland.exe`，再回来刷新。

**岛出现了但显示「未连接 MoeKoe Music」？**
打开 MoeKoe 的设置开启 **API 模式**，然后播放一首歌。

**按钮点了没反应？**
确认 MoeKoe 正在播放（SMTC 会话需要播放器处于活动状态）。

**卸载后组件还在运行？**
在插件弹窗点「退出组件」，或任务管理器结束 `MoeKoeIsland.exe`。
